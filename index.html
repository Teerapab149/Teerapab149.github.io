01 — บริบทและโจทย์

ทำไมระบบเลือกตั้งถึงไม่ใช่แค่ฟอร์มที่กดส่งได้

ผมรับผิดชอบทั้งโปรเจกต์คนเดียว ตั้งแต่คุยความต้องการกับคณะกรรมการเลือกตั้ง ออกแบบฐานข้อมูล ออกแบบวิธีเก็บบัตรลงคะแนน ทำหน้าเว็บทั้งหมด ไปจนถึงเขียนเอกสารส่งมอบ ให้ทีมสโมสรรุ่นถัดไปที่ไม่มีใครเป็นโปรแกรมเมอร์

01

ความน่าเชื่อถือของผล

ถ้าคะแนนออกมาสูสี ต้องมีวิธีพิสูจน์ทางเทคนิคว่าไม่มีใครแก้ ไม่ใช่แค่ให้เชื่อกรรมการ

02

ความลับของบัตร

ระบบออนไลน์ที่เก็บ “user คนนี้เลือกพรรคนี้” ไว้แถวเดียวกัน แปลว่าใครเข้าถึงฐานข้อมูลได้ก็รู้หมด — ผิดหลักการเลือกตั้งลับ

03

กันโหวตซ้ำจริง

ต้องกันได้แม้ผู้ใช้กดพร้อมกันหลายแท็บ ไม่ใช่กันได้เฉพาะตอนเน็ตช้าและโชคดี

04

ส่งต่อได้ทุกปี

ทีมสโมสรเปลี่ยนทุกปีและไม่มีใครเขียนโค้ด ระบบต้องเปลี่ยนปี เปลี่ยนรายชื่อ เปลี่ยนหน้าตาเว็บได้โดยไม่แตะโค้ด

05

หน้าตาที่คนอยากเข้า

เว็บราชการแบบเดิมทำให้นักศึกษาไม่อยากกดเข้ามา ต้องดูร่วมสมัยและใช้บนมือถือได้จริง

06

ผลคะแนนต้องปิดจนถึงเวลา

คะแนนระหว่างทางชี้นำคนที่ยังไม่โหวต จึงต้องปิดตั้งแต่ชั้น API ไม่ใช่แค่ซ่อนปุ่มใน UI

03 — จุดที่ยากที่สุด

บัตรลงคะแนนนิรนามที่ตรวจการแก้ไขได้

ออกแบบเองทั้งชุด ใช้ node:crypto ล้วน ไม่เพิ่ม dependency ใหม่แม้แต่ตัวเดียว เป้าหมายคือสองอย่างที่ปกติขัดกัน — ตรวจสอบย้อนหลังได้ แต่สืบกลับหาคนโหวตไม่ได้

01

แยกตัวตนออกจากตัวเลือก

ตอนโหวต ระบบเขียนสองที่คนละตาราง — ตีตรา isVoted ที่ผู้ใช้ และหย่อนบัตรที่เข้ารหัสแล้วลงตาราง Ballot ไม่มีคีย์ใดเชื่อมสองสิ่งนี้เข้าหากัน คอลัมน์ที่เคยผูกไว้ถูกลบทิ้งอย่างตั้งใจ

02

เข้ารหัสบัตรด้วย RSA-OAEP + nonce

ข้อความก่อนเข้ารหัสคือ { c: candidateId, n: nonce 128-bit } — nonce ทำให้บัตรที่เลือกพรรคเดียวกันได้ ciphertext ไม่ซ้ำกัน ปิดช่องเดาแบบ dictionary บนช่วงค่า candidate id ที่มีอยู่ไม่กี่ค่า

03

ร้อยเป็น hash chain ด้วย HMAC

บัตรทุกใบเก็บ prevHash และ rowHash = HMAC(secret, prevHash‖payload‖seq) ถ้ามีใครลบ แทรก หรือแก้บัตรกลางตาราง โซ่จะขาดที่จุดนั้นทันที ตรวจได้ทั้งตารางด้วยสคริปต์เดียว

04

เวลาก็เป็นข้อมูลรั่ว จึงเก็บแค่ระดับชั่วโมง

ถ้าบัตรเก็บเวลาแบบละเอียด ก็เอาไป join กับเวลาที่ผู้ใช้กดโหวตเพื่อจับคู่กลับได้ ตาราง Ballot จึงเก็บแค่ช่วงชั่วโมงหยาบ ๆ ส่วนเวลาละเอียดอยู่กับผู้ใช้เองซึ่งไม่ใช่ความลับ

05

กุญแจถอดรหัสไม่เคยอยู่บนเซิร์ฟเวอร์

ทำ key ceremony ปีละครั้งบนเครื่อง offline พิมพ์ private key ลงกระดาษแบ่งเก็บระหว่างเจ้าหน้าที่กับอาจารย์ที่ปรึกษา บนเซิร์ฟเวอร์มีแค่ public key — ต่อให้ยึดเซิร์ฟเวอร์ได้ก็ถอดรหัสบัตรไม่ได้

06

สิทธิ์ระดับฐานข้อมูล: แอปทำได้แค่ INSERT

บน production รัน grants ให้ user ของแอปมีสิทธิ์แค่เพิ่มบัตร ไม่มี UPDATE ไม่มี DELETE — การเลือกตั้งที่จบแล้วจึงแก้ไม่ได้แม้ผ่านโค้ดของแอปเอง

Fail closed — ถ้าตัวแปรกุญแจบนเซิร์ฟเวอร์ไม่ครบ endpoint โหวตตอบ 503 ทันที ไม่มี fallback ไปเก็บตัวเลือกแบบอ่านได้เด็ดขาด ระบบยอมปิดรับโหวต ดีกว่ายอมเก็บบัตรที่ไม่เป็นความลับ

04 — concurrency

หนึ่งคนหนึ่งเสียง ตอนที่สองคำขอมาถึงพร้อมกัน

วิธีเดิมคือ “เช็คว่าโหวตยัง แล้วค่อยบันทึก” ซึ่งมีช่องว่างระหว่างสองขั้น (TOCTOU) ถ้าผู้ใช้กดสองแท็บพร้อมกัน ทั้งคู่อาจผ่านการเช็คแล้วบันทึกทั้งคู่ คำตอบคือธุรกรรมเดียวที่ให้การรับประกันสามอย่างพร้อมกัน

src/app/api/vote/route.js
// (a) TOCTOU one-shot · (b) chain serialization · (c) tally — ในธุรกรรมเดียว
const outcome = await db.$transaction(async (tx) => {
  // (a) compare-and-set: มีคำขอเดียวเท่านั้นที่พลิก flag ได้ → count === 1
  const claim = await tx.user.updateMany({
    where: { id: user.id, isVoted: false },
    data:  { isVoted: true, votedAt },
  });
  if (claim.count === 0) return "ALREADY_VOTED";

  // (b) SELECT ... FOR UPDATE บนแถว ChainHead — คำขอที่ชนกันเรียงคิวกัน
  //     ทุกใบจึงได้ prevHash ที่ถูกต้องจริง โซ่ไม่ขาดแม้โหวตพร้อมกันเป๊ะ
  await appendBallotTx(tx, { payload, hourBucket, chainSecret });

  // (c) นับคะแนนแบบ atomic
  await tx.candidate.update({
    where: { id: parsedId },

เข้ารหัสก่อนเข้าธุรกรรม

ciphertext ไม่ได้ขึ้นกับสถานะของโซ่ จึงคำนวณไว้ก่อนได้ ทำให้ถือ row lock สั้นที่สุดเท่าที่เป็นไปได้

พิสูจน์ด้วยเทสต์ ไม่ใช่ด้วยเหตุผล

e2e ยิงสองคำขอพร้อมกันจากผู้ใช้คนเดียว ต้องสำเร็จหนึ่ง ปฏิเสธหนึ่ง และคะแนนรวมต้องเพิ่มขึ้นหนึ่ง

Rate limit ซ้อนอีกชั้น

จำกัดจำนวนคำขอต่อผู้ใช้บน endpoint โหวตและ login เพื่อกันการยิงรัว แม้ตัวกันโหวตซ้ำจะรับมือได้อยู่แล้ว

05 — ระบบธีม

หน้าตาเว็บทั้งระบบ เปลี่ยนได้จาก admin คลิกเดียว

6 ตระกูล 23 ธีม แต่ละตระกูลมี layout ของตัวเองครบทุกหน้า ไม่ใช่แค่เปลี่ยนสี ทั้งหมดมาจากไฟล์ palette ไฟล์เดียวต่อตระกูล — เพิ่มธีมใหม่คือแก้ 3 จุด ที่เหลือไหลตามทั้งระบบ

23 ธีม หน้าเดียวกัน

ทุกภาพด้านล่างคือหน้าแรกเดียวกัน ต่างกันแค่ธีมที่ active — คลิกเพื่อดูเต็ม

Token สองชั้น

Layer 1 คือสีระดับธีม Layer 2 คือตัวแปรระดับ element โดยบังคับว่าตัวแปรที่เป็นสีต้องอ้าง token เสมอ ห้ามใส่ hex ตรง ๆ

พรีวิวต้องตรงกับของจริง

ตัวที่ใช้พรีวิวกับตัวที่ render จริงต้อง map ค่าตรงกัน มี invariant คุมไว้ 7 ข้อ เพราะพรีวิวที่โกหกคือฟีเจอร์ที่อันตรายกว่าไม่มีพรีวิว

ลองก่อนเลือกได้จริง

หน้าพรีวิวเดินได้ทั้ง flow (home → login → vote → success) โดยไม่แตะฐานข้อมูล คนที่ไม่ใช่ dev จึงตัดสินใจจากการลองใช้ ไม่ใช่จากภาพนิ่ง

06 — UX / UI

เกณฑ์ที่ใช้ตัดสินงานออกแบบ

ตั้งเกณฑ์ไว้ก่อนลงมือ และทุกข้อต้องตรวจได้จริงไม่ใช่ความรู้สึก หลักคือสวยจาก craft พื้นฐาน ไม่ใช่จาก gimmick — ไม่มี 3D ไม่มี particle ไม่มี loading ที่นานเพื่อความเท่

มิติเกณฑ์ที่ต้องผ่าน
Typographyไม่เกิน 3 ระดับต่อวิว · line-height 1.1 หัวเรื่อง / 1.6 เนื้อหา · ตัวเลขสถิติใช้ tabular-nums เพื่อไม่ให้ตัวเลขเต้นตอนนับ
Spacingจังหวะ 4/8px ตลอด · whitespace ใจกว้าง · ไม่มี element ชนกันหรือชิดขอบโดยไม่ตั้งใจ
Colourcontrast เนื้อหา ≥ 4.5:1 หัวเรื่องใหญ่ ≥ 3:1 · ไม่เกิน 3 สีต่อวิว
Motionใช้เมื่อมีความหมายเท่านั้น · 150-300ms ease-out · เคารพ prefers-reduced-motion
Hierarchyทุกหน้าตอบได้ใน 1 วินาทีว่า “หน้าอะไร ต้องทำอะไรต่อ” · CTA หลักหนึ่งเดียวเด่นสุด

Mobile-first เป็นด่าน ไม่ใช่คำโฆษณา

ทุกหน้ารีวิวที่ 375px ก่อน desktop เสมอ เพราะผู้ใช้จริงเกือบทั้งหมดโหวตจากมือถือระหว่างเดินอยู่ในคณะ — mobile ต้องถูกออกแบบ ไม่ใช่ desktop ที่ย่อลงมา

การตัดสินใจที่เล่าได้

01

พรรคเดียวต้องมี 3 ทางเลือก

เมื่อมีผู้สมัครพรรคเดียว การให้กดได้แค่ “เลือก” คือการบังคับ บัตรจึงเปลี่ยนเป็น รับรอง / ไม่รับรอง / งดออกเสียง พร้อมสี semantic คงที่ที่ ไม่เปลี่ยนตามธีม เพราะความหมายของสีสำคัญกว่าความสวยของพาเลตต์

02

ผลที่ยังไม่ถึงเวลา ต้องออกแบบหน้า “ล็อก”

ไม่ใช่ซ่อนเมนูแล้วปล่อยให้งง คนที่กดเข้ามาต้องรู้ว่าทำไมยังดูไม่ได้และดูได้เมื่อไหร่ ส่วนคะแนนถูกปิดตั้งแต่ชั้น API มีเทสต์คุมว่าไม่รั่ว

03

ห้ามซ่อนเนื้อหาสำคัญไว้หลัง animation

กติกาที่ตั้งขึ้นหลังเจอของจริง — บัตรลงคะแนนเคยตั้ง opacity เป็น 0 รอ reveal แล้ว reveal ไม่ทำงานบนบางเครื่อง บัตรหายทั้งหน้า ตั้งแต่นั้นบัตร รายชื่อพรรค และผลคะแนน ห้ามพึ่ง JS reveal และตรวจด้วย computed style จริง

04

ปุ่มรองห้ามแย่งซีน

บทเรียนจากหน้าผลคะแนนที่ปุ่มรองเด่นกว่า CTA หลักจนคนกดผิดทาง แก้ด้วยการลดน้ำหนักปุ่มรอง ไม่ใช่เพิ่มน้ำหนักปุ่มหลัก

05

แต่ละธีมมีพิธีกรรมของตัวเอง

Verdure จบด้วยการประทับ wax seal · Receipt Paper เป็นม้วนใบเสร็จที่หย่อนลงหีบ · Gumroad เป็นนีโอบรูทัลสีจัด เพราะวินาทีที่กดโหวตเสร็จควรรู้สึกว่าเสียงถูกนับแล้ว ไม่ใช่แค่ขึ้นคำว่า success

06

ตัด editor ที่สร้างมากับมือทิ้ง

ระบบเคยมี editor แบบ Canva ให้ admin ลากวางเอง ทำไปไกลแล้วตัดสินใจทิ้ง เพราะสิ่งที่ผู้ใช้ต้องการจริงคือหน้าตาที่หลากหลายและพร้อมใช้ ไม่ใช่เครื่องมือออกแบบที่ไม่มีคนดูแลต่อ

ทุกคำสั่งของ admin ถูกบันทึก และปุ่มล้างข้อมูลถูกล็อกไว้ระหว่างที่การโหวตยังเปิดอยู่ ต้องสั่งหยุดระบบก่อนเท่านั้น

preflight → archive ปีเก่า → import รายชื่อใหม่ → ตั้งวันและเลือกธีมในหน้า admin → ทำ key ceremony ชุดใหม่ของปีนั้น

ฐานข้อมูลทดสอบที่แตะของจริงไม่ได้

ชุด e2e สร้าง DB ของตัวเองบนพอร์ตแยก และทุกคำสั่งลบ/ล้างมี guard บังคับตรวจชื่อ DB ก่อนเสมอ

08 — คุณภาพ

ด่านที่ต้องผ่านก่อน deploy

ชั้นครอบคลุมอะไร
buildต้อง compile ผ่านทั้ง 33 หน้า ไม่มี error
smoke · 15 เคสAPI สาธารณะไม่รั่วคะแนน · admin API ตอบ 401 ทั้งเมื่อไม่มี auth และเมื่อปลอม cookie · login ติด rate limit 429 · โหวตต้องมี session · invariants ของ role และสิทธิ์
e2e · 35 เคสโหวตครบวงจร · โหวตซ้ำและยิงพร้อมกัน · งดออกเสียง · หน้าปิดหีบ · admin console
readinessด่านสุดท้ายในหน้า admin ตรวจ 14 รายการก่อนเปิดหีบจริง

ลำดับ gate คือ build → smoke → e2e → readiness และมีเอกสารกำกับครบ: checklist สำหรับ deploy, runbook สำหรับผู้ดูแล, ใบขอฐานข้อมูลสำหรับฝ่าย IT และ pitfall log 125 ข้อที่บันทึกทุกบทเรียนที่เคยเจ็บมา เพื่อไม่ให้ผิดซ้ำ

09 — บันทึกตรงไปตรงมา

สิ่งที่ควรพูดให้ตรง

  • สถานะ — ระบบพัฒนาเสร็จและผ่านด่าน build / smoke / e2e แล้ว ขั้นตอนสุดท้ายคือ deploy ด้วย Docker ร่วมกับฝ่าย IT ของคณะ
  • ใช้ AI ช่วยพัฒนา — ผมใช้ AI เป็นคู่คิดตลอดโปรเจกต์ โดยการตัดสินใจเชิงสถาปัตยกรรมและความปลอดภัยทั้งหมดเป็นของผม และเขียนระเบียบการทำงานกับ pitfall log ไว้เป็นเอกสารเพื่อไม่ให้ผิดซ้ำ
  • ภาพทั้งหมดในหน้านี้ — ถ่ายจากหน้าพรีวิวของระบบที่ใช้ข้อมูลจำลองล้วน ไม่มีชื่อหรือรหัสนักศึกษาจริงปรากฏที่ใดเลย
